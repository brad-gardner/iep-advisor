# Design Discussion: Multilingual site (English + Spanish)

**Date:** 2026-10-06
**Feature:** Make every page, email, PDF, server message and AI response follow the user's language. Ship English and Spanish, with Spanish translated page by page as each feature is converted.

## Decisions already made (2026-10-06 conversation)

- **Scope:** everything, delivered in phases. Spanish lands for each page as that page is converted.
- **What follows the language besides on-screen text:** AI output, emails, PDF exports and API messages.
- **Preference:** detect the browser's native language as well as storing a choice on the account.

## Current State

- **No i18n anywhere.** `web/index.html` hard-codes `lang="en"`. There's no i18n library, and nothing reads `navigator.language` or `Accept-Language`. The ~420 non-test components (≈48k lines, `web/src/features/*`, `web/src/components/*`) contain English literals directly.
- **Shared chrome:**
  - `components/layouts/{main-layout,auth-layout,sidebar}.tsx`: the sidebar has 18 nav labels.
  - Shared UI defaults: `confirm-dialog` "Cancel", `pagination`, `modal`/`drawer` "Close dialog", `spinner`, `table`, `pdf-viewer`, `rich-text-editor-impl` toolbar, toasts.
- **Label maps:** about 30 maps turn enum codes into English. Examples are `educator/types.ts` `DISABILITY_CATEGORY_LABELS`, `meetings/types.ts` `MEETING_TYPE_LABELS`, plus several local and duplicated maps.
- **Dates:**
  - `lib/format-date.ts` (61 importers) uses the browser default locale.
  - 37 files call `toLocale*`/`Intl` directly, and 5 hard-code `'en-US'`.
- **Current user:**
  - Loaded by `features/auth/stores/auth-context.tsx` from `GET /api/auth/me` (`UserDto` in `Api/DTOs/Auth/LoginResponse.cs`).
  - The profile page is `features/auth/components/profile-page.tsx`.
  - `User` has no language field. `SchoolStudent.HomeLanguage` is only stored and displayed.
- **API messages:**
  - About 700 `ServiceResult.FailureResult(...)` calls, about 364 of them literal strings.
  - The web shows them through `lib/api-error.ts` `apiErrorMessage(err, fallback)`, which is used in 81 files.
- **Emails:** every subject and body is built inline in `EmailService.cs` and queued through `OutboundEmailQueue`.
  - The 13 kinds include password reset, share, school-link, student, staff and beta invites, the account-deletion cancel link, magic link, meeting invitation/update/cancel with .ics, generic notification, and digest.
  - Notification titles and bodies are written as English text at creation time by about 10 services.
- **AI:** all calls go through `ClaudeClient`. Prompts live in:
  - `AdvocatePrompts`, `AssistPrompts`, `DraftPrompts` and `DraftPromptBuilder`;
  - inline prompts in MeetingPrep, IepAssist, StudentWorkspace, Iep/EtrProcessing (the parsers), AnalysisRun and ProgressReportAnalysis.

  Canned English user-facing strings (disclaimer, unavailable message, usage-cap message, "New conversation") live in those prompt classes.
- **PDFs** (QuestPDF):
  - `IepVersionPdfDocument` and `AuthoredDocumentPdfDocument` have hard-coded labels ("Page", Goals, Services, Signatures, Attended…).
  - They are generated by background workers (`IepVersionPdfWorker`, `AuthoredDocumentPdfWorker`).
- **Tests:** 168 web test files. About 600 queries use English text (getByRole name, getByText, getByLabelText); about 1,476 use test ids.

## Patterns to Follow

- **Feature-folder layout** (`features/<feature>/{components,pages,lib,types.ts}`): translation namespaces follow the same boundaries.
- **The `lib/api-error.ts` fallback pattern:** the fallbacks become translation keys.
- **Shared label helpers**, e.g. `children/lib/child-profile-options.ts`: option labels already go through one function, so the translation lookup goes there.
- **API response envelope** (`ApiResponse {success, message}`) and `ServiceResult`: keep the shapes and localize `Message`.
- **Prompt hardening** (`PromptText.Data` / `DraftPromptBuilder.Data`): the language instruction is added the same way, as one appended system line, never interpolated from user text.

## Desired End State

### Web

- **Libraries:** `i18next` 26 + `react-i18next` 17 + `i18next-browser-languagedetector` 8.
- **Resources:** `web/src/locales/{en,es}/<namespace>.json`, one namespace per feature plus `common` (shell, shared UI, enum labels).
  - Spanish namespaces are lazy-loaded with `import.meta.glob`; English is bundled.
  - Typed keys (`CustomTypeOptions`, derived from `en`) make a missing or misspelled key a `tsc` error.
- **Language resolution**, in order:
  1. the signed-in user's saved `preferredLanguage`;
  2. a choice made before login (localStorage);
  3. the browser's `navigator.languages` (`es-*` → `es`);
  4. `en`.

  The first signed-in load with no saved preference saves the resolved language, so emails and AI know it.
- **Switching:** a language switcher on the auth pages and in the sidebar (English / Español), plus a Language setting on Profile. Switching updates `<html lang>` and the document title, and persists to the account.
- **Formatting:** all dates and numbers go through `Intl` with the active language (`formatDate`, `relativeTime`, meeting times). There is no hard-coded `'en-US'`.
- **Label maps:** become `t('common:disabilityCategory.Autism')`-style lookups behind small helper functions, so call sites don't change shape. Stored values stay English or enum codes; only the display is translated.
- **API calls:** axios sends `Accept-Language: <active language>` on every request.
- **Guard rails:**
  - Each converted folder turns on `eslint-plugin-i18next` `no-literal-string` in JSX text and attributes (`aria-label`, `title`, `placeholder`, `label`) through `eslint.config.js` overrides. This ratchets folder by folder without moving the global lint baseline.
  - A key-parity test asserts that every `en` key exists in `es` and is not empty.

### API

- **Language field:** `User.PreferredLanguage` (`nvarchar(10)`, nullable, values `en` or `es`), via migration.
  - Exposed on `UserDto`.
  - Accepted by `PUT /api/auth/me`, validated against the supported list.
- **Request culture:** ASP.NET Core `RequestLocalization`, supporting `en` (default) and `es`.
  - Order: the user's saved preference for authenticated requests, then `Accept-Language`.
  - It sets `CurrentUICulture` for the request.
- **Server messages:** strings move to `.resx` resources (`Resources/Messages.resx` plus `Messages.es.resx`) read through `IStringLocalizer<Messages>`.
  - `ServiceResult` messages are localized at the point they are created.
  - Work outside a request (workers, emails, notifications) uses an explicit culture scope set to the recipient's `PreferredLanguage ?? "en"`.
- **Emails:** each email kind is rendered in the recipient's language.
  - An invitee who has no account yet gets the sender's language. The invite links carry `?lang=`, so the landing page opens in that language.
  - The .ics summary and description are localized too.
- **Notifications:** titles and bodies are created in the recipient's language. Rows stored before this change stay English.
- **AI:** one shared `ResponseLanguage` helper appends "Respond in Spanish (neutral Latin American, formal usted); keep acronyms IEP/ETR/IDEA and quoted document text as written" when the requester's culture is `es`.
  - This applies to Advocate, meeting prep, draft questions and explanations, meeting summary and brief, analysis synthesis, progress-report analysis, IEP/document assist and student workspace.
  - Generated artifacts store the language they were generated in (e.g. `AnalysisRun.Language`, the meeting-prep row). When the viewer's language differs, the UI says "Generated in English" rather than re-generating silently.
  - **Parsers (`IepProcessingService`, `EtrProcessingService`) are not changed.** Extraction must keep the source document's text exactly.
  - Canned AI strings (disclaimer, cap message, default title) move to resources.
- **PDFs:** label sets are passed in by culture.
  - An authored or IEP-version PDF downloaded by a Spanish user is rendered with Spanish labels.
  - Cache and blob keys include the language, so English and Spanish copies don't overwrite each other.
  - Document content and template field labels are district data and stay as written.

### Not translated (by design)

- User-entered and district content: IEP/ETR text, authored document values, district template labels, journal entries, notes.
- Knowledge-base article bodies, which are stored content: a separate content-translation item (see Open Questions).
- Stored enum codes and readable stored strings (e.g. ChildProfile "8th"). Only their display is translated.

## Design Decisions

1. **react-i18next over react-intl/Lingui.** It is the most widely used, has no compile step (Lingui needs a macro and extraction), supports lazy namespaces, and has first-class TypeScript key typing.
2. **Namespace per feature, English bundled, Spanish lazy.** English always renders without a flash. Spanish costs only the namespaces a page uses.
3. **English source text lives in `en/*.json`, not inline defaults.** One source of truth, and typed keys catch drift. The parity test catches missing Spanish.
4. **Server-side `.resx` + `IStringLocalizer` for API messages.** This is standard ASP.NET Core and leaves the 81 web call sites unchanged, because the message arrives already localized. Converting 700 results to error codes was rejected: too large, and it couples web and API.
5. **Culture per recipient, not per sender, for emails and notifications.** The person reading it is who matters. Pre-account invitees use the sender's language and get `?lang=` on the link.
6. **Translation tone:** neutral Latin American Spanish with formal "usted", the audience being US families. The glossary in `docs/i18n/glossary-es.md` follows US Department of Education/OSEP Spanish IDEA terminology, e.g. "Programa de Educación Individualizado (IEP)", "Evaluación del Equipo de Evaluación (ETR)", "plan de transición". Acronyms are kept.
7. **Spanish is machine-drafted (by Claude) and flagged for review.** `docs/i18n/README.md` records the review status per namespace. Spanish is functional immediately, but should be reviewed by a native speaker, ideally someone in special education, before it's marketed.
8. **Lint ratchet per folder instead of a global switch.** The CI baseline (≤36) stays green while folders convert. The rule becomes global in the last phase.
9. **Tests stay English by default.** `test/setup.ts` initializes i18n synchronously with `en`, so the ~600 text queries keep working. Each phase adds Spanish render tests for its pages.

## Testing Strategy

- **Unit:**
  - key parity `en` ↔ `es`, with no empty values;
  - language resolution order (saved → pre-login → browser → en);
  - `formatDate`/`relativeTime` per locale;
  - the label helpers.
- **Component:** for every converted page, one test renders it in Spanish and asserts the key headings and controls are Spanish (by role and name), plus that no raw keys (`ns:key`) are visible.
- **API:**
  - `RequestLocalization` picks the saved preference over `Accept-Language`;
  - `ServiceResult` messages come back in Spanish;
  - each email kind renders in the recipient's language;
  - AI prompt builders append the language line only for `es`, and the parsers never get it;
  - the PDF label set switches, and cache keys include the language.
- **Type/lint:** `tsc` fails on unknown keys, and the converted folders pass `no-literal-string`.
- **Manual/QA:**
  - Spanish browser → login page in Spanish → sign in → the account stores `es`.
  - Walk each phase's pages, trigger an email and a PDF, and ask the Advocate a question.
